# 0.3.4 功能修复与验证

日期：2026-11-22。配套版本为 `dsh-btw-explore 0.3.4` 和 `dsh-message-toolbar 1.11.1`，实际宿主为安装版 DSH `0.2.2-rc.5`。

## 修复内容

- **开卡与移除并发（F01）**：原生会话准备期间，卡片及其祖先不能被移除。准备使用独立 token、20 秒租约和 750 毫秒心跳；迟到完成必须通过有效租约和身份检查。失去租约或卡片已被移除时，不会再返回成功，也不会删除 DSH 对话。
- **多宿主同时建同卡（F02）**：在 SQLite 事务内检查卡片和来源，预留唯一的原生会话。另一个实例收到可重试的 409，不再触发唯一键异常；不同来源请求不会被错误合并。恢复预留会话时优先解析已有身份，被其他 writer 占用时提示重试，避免宿主 `create` 的备用分配路径创建无关会话。
- **保存回答后脱离子卡（F03）**：工具栏把版本导航交给当前子卡。探索插件验证版本来源后持久化绑定，在同一卡内切换原生 SessionProvider。旧、新版本共享卡片固定的来源摘录；关闭重开和宿主重启都会恢复当前选择。工具栏重生成在客户端完成导航前就可能发送请求，因此在宿主 pre-step 阶段登记可信版本归属，让首次请求也能获得来源。

数据库升级到 schema 4，保留旧卡、原生绑定、来源内容和活动的旧式 writer。版本别名随卡片一起移除；任一关联版本正在运行时，仍保护该卡及祖先。版本切换验证同一工作目录及工具栏自身的来源标记，不接受其他卡的会话或普通 DSH fork。

本次兼容修复需要同时更新两个插件。工具栏 `1.11.0` 没有嵌入导航协议，保存仍会打开主窗口。保存期间关闭、覆盖或重新挂载子卡会拒绝迟到导航；已经完成的版本保存仍保留，可从卡片或版本树回看。

## 自动化

动效测试曾在负载较高时失败：fixture 手动控制 WAAPI 的 `finished`，却让真实 260 毫秒兜底先结束动画。加入 320 毫秒等待稳定复现后，只在测试装载边界注入独立时钟。新增兜底进入/退出、旧期限不影响新切换和真实计时器退出三项测试，生产动效没有改变。

工具栏在合入其远端最新提交后，完整 `npm test` 通过 host 和既有客户端检查；Node suite **190 项中 189 项通过、1 项因 Windows 文件符号链接权限跳过**。两个仓库的 `git diff --check` 均通过。

## 双安装包与真实宿主

通过 DSH 的插件安装命令，将两个 `.tgz` 安装到新的临时 profile，未使用源码 link。`test/host-smoke.mjs` 的 `--package` 与 `--toolbar-package` 分别接受两个归档路径；加 `--serve` 可继续浏览器检查，按 Enter 正常退出并清理服务。

**22 个宿主检查点通过**，包括认证、插件加载、真实原生对话、脚本模型 SSE、精确来源、主聊天隔离、工具栏编辑后的绑定与续问、重生成首次请求，以及真实宿主进程重启后的版本选择和来源恢复。每个测试服务请求完成时即时保存 provider messages，避免只保留 GUI 操作前的请求。

浏览器实际执行了以下链路：

1. 从原主聊天的探索树打开已有引用子卡，编辑回答并保存；覆盖页仍在，同一卡 ID 保持不变，主窗口仍选中原主聊天。
2. 切到旧回答，确认编辑补充消失；切回编辑版本，确认补充恢复。两次切换均留在子卡。
3. 返回卡片树，再打开对话，确认仍为编辑版本。
4. 用原生输入框发送续问，界面完成两轮问答。读取服务实际收到的请求，确认 assistant 历史包含保存的补充，来源 reminder 仍包含原问题和选中的引用。

GUI 前后的主聊天原有 16 条事件逐条相同。首次在原生界面打开这个冷会话时，宿主恢复路径自然增加一条 `session/end-seed` 生命周期标记；没有新增主聊天问答或模型步骤，因此不将整个事件日志描述为字节不变。

归档内文件逐一与工作树核对，必需入口和生成客户端齐全，没有临时 CSV。最终补充验证文档后重新打包，并核对生产文件与已完成宿主/GUI 验证的归档完全一致。

## 验证边界

模型为仅监听本机的脚本式 SSE 服务，验证的是实际请求内容、交互、持久化和上下文管道；未评价真实模型回答质量。用户的桌面 profile、真实模型提供商和 DSH 安装文件未参与修改，桌面实例未重启。

原生准备、版本归属和前端导航分别由代理实现或交叉审查，主代理复核差异并执行全量测试、安装包联测和 GUI 操作。本次临时宿主和模拟模型服务均已停止。
